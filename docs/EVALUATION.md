# 评测方法

## 1. 为什么要自己定指标

"多模态问答效果不错"不是可以被检验的说法。可检验的说法至少要有三件事：
**问题从哪来、答对怎么判、证据是否真的对上**。这份文档把三者写死，
任何一次 `python -m visioncite.eval.run` 都产出同样口径的数字。

## 2. 语料

- 由 `eval/templates.py` 程序化渲染 4 类共 8 张页面（invoice / table / chart / slide × 2 份），
  每页 4–5 个问题，共 **36 题**（28 可答、8 不可答）。
- 标准答案与**证据框**来自绘制时的 `textbbox` 坐标，因此是真的"精确标注"，
  不存在人工标注对齐误差。
- 局限：合成语料分布简单（干净背景、规整排版、无手写、无倾斜、无遮挡），
  数字必然好于真实扫描件。这一点在 README、LIMITATIONS、报告里都写明。

## 3. 指标定义

| 指标 | 定义 | 统计范围 |
|---|---|---|
| AnswerAcc | 标准答案（归一化后）出现在预测答案中 | 可答且实际作答 |
| EM | 归一化后完全相等 | 可答且实际作答 |
| F1 | 中文 bigram 的 token 级 F1 | 可答且实际作答 |
| Cite-P | 命中引用数 / 引用总数，命中判据 IoU ≥ 0.5 | 可答且实际作答 |
| Cite-R | 是否存在命中引用（0/1 的均值） | 可答且实际作答 |
| Coverage | 实际作答数 / 总题数 | 全部 |
| AbstainAcc | 可答未弃 + 不可答已弃 的比例 | 全部 |
| ECE | 10 箱校准误差，"正确" = AnswerAcc=1 且未弃答 | 全部 |
| p50 / p95 | `answer_question` 端到端耗时 | 全部 |

**为什么 EM 通常很低？** 抽取式系统返回的是"包含答案的整句"，
而标准答案是"答案值本身"。EM 用来观察抽取粒度，不作为主指标；
对外讲效果时用 AnswerAcc + Cite-P/R。

**为什么 AnswerAcc 会接近 1？** 因为答案来自检索到的证据句，只要检索对了，
答案里自然包含答案值。这说明**当前瓶颈在检索与弃答，不在"生成"**——
这也是抽取式基线最大的价值。

## 4. 三档消融

| 模式 | 做法 | 想回答的问题 |
|---|---|---|
| page | 每页压成一个区域，不做版面切分 | 版面切分本身值多少 |
| layout | XY-cut 区域 + BM25 | 文本结构能做到多好 |
| hybrid | 再加 CLIP 视觉召回（RRF 融合） | 视觉一路带来多少增量 |

配对方式：同一批 36 道题、同一份索引参数，只改检索路径。
报告里给 95% bootstrap 区间；样本量小，区间宽，不做过强的显著性宣称。

## 5. 复现

```bash
# 生成语料（首次）
python -c "from pathlib import Path; from visioncite.eval.corpus_gen import generate_corpus; generate_corpus(Path('corpus'))"

# 跑三档消融，输出 reports/eval-<时间>.md 与 .json
python -m visioncite.eval.run --mode all

# 只看某一档
python -m visioncite.eval.run --mode layout
```

逐样本记录在 `.json` 的 `records` 字段里，包含预测、标准答案、置信度、延迟、
是否命中引用，可以自己重算任何指标。

## 6. 已知的口径问题（不藏）

1. AnswerAcc 用"包含"判断，长答案可能"碰巧包含"标准值；因此同时报 EM 与 F1。
2. 引用命中用 IoU ≥ 0.5，与 COCO AP50 同口径；对细长文本行偏严格。
3. 置信度是启发式公式（覆盖率/领先幅度/得分），ECE 实测偏高说明**过自信**，
   正确做法是温度缩放或 isotonic 校准，当前未做（见 ROADMAP）。
4. 延迟只统计问答阶段，不含建索引（OCR 与 CLIP 编码是主要成本，单独记录在建索引日志里）。
